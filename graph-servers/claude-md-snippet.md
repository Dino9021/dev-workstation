# CLAUDE.md snippet — how an AI agent should use the two code-graph servers

Installing the servers is not enough. Without a written rule an agent picks whichever
tool it happened to see first, asks both the same question, and trusts a stale index.
This file is the rule.

**This file is English only, and it is the one the installer injects.** A Traditional
Chinese translation lives in [`claude-md-snippet.zh-TW.md`](claude-md-snippet.zh-TW.md)
for human reference. Keep the two apart: a mixed-language block doubles the tokens an
agent reads for one rule, and the two halves drift.

**How to use it**: run `install.ps1 -PatchOnly -Repo <repo-root>` and the installer
writes the block below into that project's **`CLAUDE.local.md`** between its own markers
— a re-run updates it in place. Or copy everything below the horizontal line by hand.

**Why `CLAUDE.local.md` and not `CLAUDE.md`.** This rule is personal harness config: it
names MCP servers that exist only if you ran the installer, and it cites
`.claude/skills/gitnexus/` and `.gitnexus/run.cjs`, both conventionally git-ignored. In
the shared, version-controlled `CLAUDE.md` it hands a fresh cloner instructions they
cannot follow. Claude Code reads `CLAUDE.local.md` natively and the installer makes sure
git ignores it. Pass `-SharedAgentDoc` if you genuinely want it in `CLAUDE.md`, and
`-NoAgentDoc` for no injection at all.

**This file is the single source of the rule.** The installer reads the text below the
`---` from here; do not duplicate the wording anywhere else. Edit here, re-run, done.

⚠️ **Paste it OUTSIDE the `<!-- gitnexus:start -->` … `<!-- gitnexus:end -->` markers.**
`gitnexus setup` generates that block and **the next `gitnexus analyze` overwrites all
of it**, so anything you write inside is lost. The generated block also says "always run
GitNexus `impact` before editing a symbol" — the snippet below deliberately supersedes
that line, and says so, because impact radius belongs to code-review-graph.

Both call sites in this repo now pass `--skip-agents-md`, so neither the installer nor
the post-commit refresh creates or restores that block. You only meet it if you run
`gitnexus analyze` by hand without the flag.

## Two code-graph servers, split by capability

**Neither server is always first choice.** Pick by the question, with no default
preference.

- **code-review-graph owns symbol lookup, structure, and impact radius.**
  `query_graph_tool` / `traverse_graph_tool` (structural queries and traversal),
  `get_architecture_overview_tool`, `get_hub_nodes_tool` / `get_bridge_nodes_tool` /
  `get_community_tool` (architecture and hubs), `get_impact_radius_tool` +
  `get_affected_flows_tool` (impact radius), `get_review_context_tool` /
  `get_minimal_context_tool` (minimal review context), `find_large_functions_tool`,
  `get_knowledge_gaps_tool`, `semantic_search_nodes_tool` (see the precondition below).
- **GitNexus owns taint, PDG, execution flow, and Cypher.** `explain` (source→sink taint,
  needs `analyze --pdg` first), `pdg_query` (control and data dependence — "what guards
  this line", "where does this value flow"), `query` / `trace` plus
  `gitnexus://repo/<repo-name>/process/{name}` (step-by-step execution flow), `cypher`
  (raw graph queries), `rename` (call-graph-aware multi-file rename).
- **Never ask both servers the same question.** It burns tokens without buying certainty.
  The two databases are fully separate (`.gitnexus/lbug` versus
  `.code-review-graph/graph.db`); they share no files and contend for no lock.
- **The one deliberate overlap — C++ callers across files.** code-review-graph's caller
  lookup resolves a name to the *definition's* file-scope node, so callers in other
  translation units are missed. Route that question to GitNexus `impact`, and give it
  both arguments: `direction: 'upstream'` (that is the "who calls this" direction) and,
  as `target`, the **`.hpp`** declaration's `target_uid` — a uid taken from an earlier
  tool result, not a bare function name. Asked against the `.cpp` definition it answers
  `impactedCount: 0`.
  ⚠️ **This does not make `impact` reliable here.** Choosing the `.hpp` uid rules out
  only one cause of a zero answer. For the other, see "What the graphs are authoritative
  for" below.
- ⚠️ **The block between `<!-- gitnexus:start -->` and `<!-- gitnexus:end -->` is
  generated by the gitnexus CLI.** Its "always run GitNexus `impact` before editing a
  symbol" line is **superseded by this section**: impact radius goes to
  code-review-graph's `get_impact_radius_tool`. Never hand-edit inside those markers; the
  next `analyze` overwrites them.

### Check index freshness before you trust an answer

| | Refreshes | Covers | When the server sees the new index |
|---|---|---|---|
| code-review-graph | ~2s after a save (resident daemon) | **code files only** | **live** (it re-reads the database on every call) |
| GitNexus | after `git commit` (post-commit hook, ~142s) | every file, including `.md` and JSON | **next session** (the index is cached when the server starts) |

Five preconditions that otherwise produce wrong answers:

1. **Uncommitted working-tree code is not in the GitNexus graph.** Commit first, or run
   **`gitnexus analyze --skip-agents-md`** by hand. **Do not drop that flag**: without it
   `analyze` appends its own `<!-- gitnexus:start -->` block to the project's `CLAUDE.md`
   and `AGENTS.md`, editing a shared, version-controlled file as a side effect of
   indexing.
2. **Non-code content (`docs/*.md`, JSON) exists only in GitNexus** — code-review-graph
   cannot see it at all.
3. **`semantic_search_nodes_tool` needs embeddings.** Zero vectors means unusable, and
   **the watch daemon does not embed new code** — re-run `code-review-graph embed` after
   substantial changes. Five-second check:
   `python -c "import sqlite3;print(sqlite3.connect(r'.code-review-graph/graph.db').execute('select count(*) from embeddings').fetchone())"`
4. **`gitnexus analyze` exits 0 even on failure.** Judge success from the output text
   (`Analysis failed`) and from `lastCommit` in `.gitnexus/meta.json` versus `HEAD` —
   never from the exit code.
5. **Do not judge index freshness from the `graph.db` file timestamp.** SQLite can write
   inside existing pages, so the mtime does not always change — which looks exactly like
   "it never ran". Read the `Last updated` line from `code-review-graph status --repo .`
   instead.

### What the graphs are authoritative for

A graph answers structure cheaply and supplies context a text search cannot, so asking it
first is the good trade. It is **not** the last word on "who calls this". On the same day,
on the same C++ function, both servers under-reported callers: code-review-graph returned
1 where there were 7, and GitNexus `impact` returned
`impactedCount: 0, epistemic: "exact"` where there were 4. `epistemic: "exact"` describes
the graph, not the code, so a wrong answer reads as a certain one.

When that caller list is load-bearing — changing a signature, deleting something, judging
"is anyone still using this" — settle it with `git grep` as well, and **include a positive
control**: search in the same run for a call site you already know exists, to prove the
pattern and the path are right. A search of the wrong place and a genuinely empty result
look identical on screen.

**A folder move or rename refused with `being used by another process` is not your fault.**
code-review-graph's watch daemon holds directory handles on Windows, so nothing inside the
watched tree can be renamed or moved. Run `code-review-graph daemon stop`, move, then start
the daemon again. The same cause blocks `git worktree remove` and folder deletion.

**Do not judge whether a symbol exists from `code-review-graph search` output.** Its JSON
echoes the query string (`"query": "..."`), so a string match "finds" a symbol that does
not exist. Query the `nodes` table instead.
