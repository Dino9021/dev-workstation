# CLAUDE.md snippet — how an AI agent should use the two code-graph servers

Installing the servers is not enough. Without a written rule an agent picks whichever
tool it happened to see first, asks both the same question, and trusts a stale index.
This file is the rule.

**How to use it**: run `install.ps1 -PatchOnly -Repo <repo-root>` and the installer
writes the block below into that project's `CLAUDE.md` between its own markers — a
re-run updates it in place. Or copy everything below the horizontal line by hand, then
delete whichever language you do not want.

**This file is the single source of the rule.** The installer reads the text below the
`---` from here; do not duplicate the wording anywhere else. Edit here, re-run, done.

⚠️ **Paste it OUTSIDE the `<!-- gitnexus:start -->` … `<!-- gitnexus:end -->` markers.**

## 兩台程式圖譜伺服器：按能力分工 | Two code-graph servers, split by capability

**兩台都不是永遠的第一順位。** 先看你要問什麼，再決定開哪一台，不要有預設偏好。

- **code-review-graph 負責:找符號、看結構、算影響範圍。** `query_graph_tool` / `traverse_graph_tool`（結構查詢與走訪）、`get_architecture_overview_tool`、`get_hub_nodes_tool` / `get_bridge_nodes_tool` / `get_community_tool`（架構與樞紐）、`get_impact_radius_tool` + `get_affected_flows_tool`（影響範圍）、`get_review_context_tool` / `get_minimal_context_tool`（審查用最小上下文）、`find_large_functions_tool`、`get_knowledge_gaps_tool`、`semantic_search_nodes_tool`（語意找符號，先看下方前提）。
- **GitNexus 負責:taint、PDG、execution flow、Cypher。** `explain`（汙染流 source→sink，需要先跑過 `analyze --pdg`）、`pdg_query`（控制/資料依賴,「誰守住這一行」「這個值流去哪」）、`query` / `trace` 與 `gitnexus://repo/<repo-name>/process/{name}`（執行流程逐步追蹤）、`cypher`（原始圖查詢）、`rename`（理解呼叫圖的多檔改名）。
- **同一個問題不要兩台都問。** 重複燒 token，換不到更高的確定性。兩台資料庫完全獨立（`.gitnexus/lbug` vs `.code-review-graph/graph.db`），不共用檔案、不搶鎖。
- ⚠️ **下方 `<!-- gitnexus:start -->` … `<!-- gitnexus:end -->` 之間的段落由 gitnexus CLI 自動產生。** 它寫「改任何符號前一律先跑 GitNexus `impact`」——**那一句以本條為準**：影響範圍走 code-review-graph 的 `get_impact_radius_tool`。標記內的文字不要手改,下次 `analyze` 會整段覆蓋。

### 查之前先確認索引夠新 | Check index freshness before trusting an answer

| | 更新時機 | 涵蓋範圍 | 伺服器何時看得到新索引 |
|---|---|---|---|
| code-review-graph | 存檔後約 2 秒（常駐 daemon） | **只有程式碼檔** | **當場**（每次呼叫重讀資料庫） |
| GitNexus | `git commit` 後（post-commit hook，約 142 秒） | 全部檔案，含 `.md`、JSON | **下一個工作階段**（索引快取在伺服器啟動的瞬間） |

四個會讓你得到錯答案的前提，動手前先確認:

1. **只改了工作區、還沒 commit 的程式,GitNexus 圖譜裡沒有。** 需要它進圖譜就先 commit,或手動跑 `gitnexus analyze`。
2. **`docs/*.md` 這類非程式碼內容只有 GitNexus 有**,code-review-graph 完全看不到。
3. **`semantic_search_nodes_tool` 需要向量。** 向量數 0 就等於不能用,而且**常駐 daemon 不會替新程式補向量**——大幅改動後要手動 `code-review-graph embed`。五秒確認:
   `python -c "import sqlite3;print(sqlite3.connect(r'.code-review-graph/graph.db').execute('select count(*) from embeddings').fetchone())"`
4. **`gitnexus analyze` 失敗也回傳 exit code 0。** 判斷成功要看輸出文字有沒有 `Analysis failed`,以及 `.gitnexus/meta.json` 的 `lastCommit` 是否等於 `HEAD`——**不要看 exit code**。

5. **別用 `graph.db` 的檔案時間（mtime）判斷索引有沒有更新。** SQLite 可能在既有頁面內寫入,主檔 mtime 不一定改變——看起來像「完全沒跑」。要判斷新鮮度看 `code-review-graph status --repo .` 的 `Last updated` 那一行。

**搬移或改名資料夾被拒（`being used by another process`）不是你的錯。** code-review-graph 的監看 daemon 在 Windows 上持有目錄句柄,被監看樹裡的資料夾不能改名或搬移。先 `code-review-graph daemon stop`,搬完再重新啟動 daemon。這也會擋掉 `git worktree remove` 與刪除資料夾。

**別用 `code-review-graph search` 的輸出判斷符號存不存在。** 它的 JSON 會回顯查詢字串（`"query": "..."`）,所以拿字串比對輸出時,一個根本不存在的符號也會「命中」。要判斷就查資料庫的 `nodes` 表。

**English** — *Two code-graph servers, split by capability.* **Neither is always first choice**; pick by the question with no default preference.

- **code-review-graph owns symbol lookup, structure, and impact radius**: `query_graph_tool`/`traverse_graph_tool`, architecture and hub/bridge/community tools, `get_impact_radius_tool` + `get_affected_flows_tool`, review-context tools, large-function and knowledge-gap scans, `semantic_search_nodes_tool` (see the precondition below).
- **GitNexus owns taint, PDG, execution flow, and Cypher**: `explain` (source→sink taint, needs `analyze --pdg` first), `pdg_query` (control/data dependence — "what guards this line", "where does this value flow"), `query`/`trace` plus the `process/{name}` resources, `cypher`, and `rename` (call-graph-aware multi-file rename).
- **Never ask both servers the same question** — it burns tokens without buying certainty. Their databases are separate, so coexistence is safe.
- ⚠️ The block between `<!-- gitnexus:start -->` and `<!-- gitnexus:end -->` is **generated by the gitnexus CLI**. Its "always run GitNexus `impact` before editing a symbol" line is **superseded by this section** (impact radius goes to code-review-graph). Never hand-edit inside the markers; the next `analyze` overwrites them.

*Freshness, before trusting an answer:* code-review-graph refreshes ~2s after a save and is **live per call**, but indexes **code files only**. GitNexus refreshes **after a commit** (~142s) and covers every file, but **caches its index at server startup**, so a finished analyze is invisible until the next session.

Four preconditions that otherwise produce wrong answers:

1. **Uncommitted working-tree code is not in the GitNexus graph.** Commit first, or run `gitnexus analyze` by hand.
2. **Non-code content (`docs/*.md`, JSON) exists only in GitNexus** — code-review-graph cannot see it at all.
3. **`semantic_search_nodes_tool` needs embeddings.** Zero vectors means unusable, and **the watch daemon does not embed new code** — re-run `code-review-graph embed` after substantial changes. Five-second check:
   `python -c "import sqlite3;print(sqlite3.connect(r'.code-review-graph/graph.db').execute('select count(*) from embeddings').fetchone())"`
4. **`gitnexus analyze` exits 0 even on failure.** Judge success from the output text (`Analysis failed`) and from `lastCommit` in `.gitnexus/meta.json` versus `HEAD` — never from the exit code.

5. **Do not judge index freshness from the `graph.db` file timestamp.** SQLite can write inside existing pages, so the mtime does not always change — which looks exactly like "it never ran". Read the `Last updated` line from `code-review-graph status --repo .` instead.

**A folder move or rename refused with `being used by another process` is not your fault.** code-review-graph's watch daemon holds directory handles on Windows, so nothing inside the watched tree can be renamed or moved. Run `code-review-graph daemon stop`, move, then start the daemon again. The same cause blocks `git worktree remove` and folder deletion.

**Do not judge whether a symbol exists from `code-review-graph search` output.** Its JSON echoes the query string (`"query": "..."`), so a string match "finds" a symbol that does not exist. Query the `nodes` table instead.
